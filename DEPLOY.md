# Развёртывание

Сайт: **https://shazram.ru** (и `www.shazram.ru`).

---

## Что где лежит

| Где | Что |
|---|---|
| `/opt/risk` | весь проект на сервере |
| `/opt/risk/deploy/.env` | секреты: домен, email для ACME, логин и bcrypt-хэш пароля. **Права 600, в git не попадает** |
| `/opt/risk/deploy/docker-compose.prod.yml` | боевой стек: `caddy`, `frontend`, `backend` |
| `/opt/risk/riskml/artifacts/` | обученные модели (приехали вместе с кодом, на сервере не обучаются) |
| docker-том `deploy_caddy_data` | сертификаты Let's Encrypt — переживают пересборку |
| `/swapfile` | swap 2 ГБ, создан до первой сборки |

Наружу открыт только Caddy (80/443). Порты бэкенда и фронтенда на хост
**не публикуются** — связь только по внутренней сети compose.

---

## Как обновить сайт

```bash
ssh -i ~/.ssh/shazram_ed25519 root@2.56.120.183
cd /opt/risk && bash deploy/deploy.sh
```

Скрипт помечает текущие образы как `:rollback`, собирает новые, поднимает и
ждёт `healthy`. Если сервисы не поднялись — **сам возвращает предыдущие образы**.
В конце подчищает старые слои: без этого 10 ГБ диска кончаются за два деплоя.

Код на сервер попадает архивом с локальной машины (git-remote у проекта нет):

```bash
# локально, из корня проекта
tar --exclude=.venv --exclude=node_modules --exclude=research --exclude=docs \
    -czf ../risk.tar.gz .
python tools/deploy_remote.py ../risk.tar.gz
```

Короткие команды — через `make -f deploy/Makefile`: `deploy`, `logs`, `ps`,
`restart`, `health`, `prune`.

## Как посмотреть логи

```bash
cd /opt/risk
docker compose --env-file deploy/.env -f deploy/docker-compose.prod.yml logs -f --tail=100
# только один сервис:
docker compose --env-file deploy/.env -f deploy/docker-compose.prod.yml logs -f caddy
```

Логи ротируются docker'ом (`/etc/docker/daemon.json`: 10 МБ × 3 файла) — на
диске в 10 ГБ это первое, что иначе его забивает.

## Как откатиться

`deploy/deploy.sh` откатывается сам при неудачном обновлении. Вручную:

```bash
cd /opt/risk
docker tag risk-backend:rollback  risk-backend:prod
docker tag risk-frontend:rollback risk-frontend:prod
docker compose --env-file deploy/.env -f deploy/docker-compose.prod.yml up -d
```

## Если сайт не открывается

Проверять по порядку, сверху вниз:

1. **DNS.** `dig +short shazram.ru` и `dig +short www.shazram.ru` — обе должны
   давать `2.56.120.183`. Если нет, дальше идти бессмысленно.
2. **Контейнеры.** `cd /opt/risk && make -f deploy/Makefile ps` — все три должны
   быть `healthy`. Если `backend` не поднимается, чаще всего это несовпадение
   версии scikit-learn с той, на которой обучены модели: смотрите
   `docker logs deploy-backend-1`.
3. **Диск.** `df -h /`. Меньше 1 ГБ — Docker начинает вести себя странно.
   Лечится `make -f deploy/Makefile prune`.
4. **Сертификат.** `docker logs deploy-caddy-1 | grep -i certificate`.
   Если Let's Encrypt отказал — почти всегда виноват DNS (пункт 1).
5. **Firewall.** `ufw status` — 80 и 443 должны быть открыты.

## Доступ

Сайт **открыт без пароля** — по решению владельца. Обоснование, почему это
приемлемо именно здесь:

* **демо-данные обезличены.** Это публичный датасет UCI: в списке номера строк
  (`429`, `433`), а не фамилии;
* **загруженные файлы не сохраняются** — обрабатываются в памяти, на диск не
  пишутся, в логи не попадают. Чужие данные на сервере не оседают;
* **сайт закрыт от индексации** — `robots.txt` с `Disallow: /` и мета-тег
  `noindex, nofollow`, так что в поиск демо не попадёт.

Что при этом остаётся риском: сервером может пользоваться кто угодно. Защита
одна — ограничение частоты запросов на стороне приложения
(`RATE_LIMIT_PER_MINUTE`, по умолчанию 60 в минуту на IP).

**Если сайт начнут загружать реальными списками с фамилиями — пароль нужно
вернуть.** Всё для этого готово: в `deploy/Caddyfile` есть закомментированный
блок, логин и bcrypt-хэш лежат в `deploy/.env`.

```bash
cd /opt/risk
# раскомментировать блок @private / basic_auth в deploy/Caddyfile, затем:
docker exec deploy-caddy-1 caddy reload --config /etc/caddy/Caddyfile
```

Перечитывание конфига идёт **без простоя** — контейнер не перезапускается.
Учтите: `docker compose up -d caddy` изменения в Caddyfile не подхватит, потому
что файл примонтирован томом и для compose контейнер выглядит неизменным.

Сменить пароль (если вернёте авторизацию):

```bash
cd /opt/risk
HASH=$(docker run --rm caddy:2.10-alpine caddy hash-password --plaintext 'НОВЫЙ')
# в .env значение должно быть с удвоенными $, иначе compose съест их как переменные
ESC=$(printf '%s' "$HASH" | sed 's/\$/$$/g')
sed -i "s|^BASIC_AUTH_HASH=.*|BASIC_AUTH_HASH=$ESC|" deploy/.env
docker exec deploy-caddy-1 caddy reload --config /etc/caddy/Caddyfile
```

## Бэкапы

**Бэкапить нечего.** Базы данных в проекте нет. Загруженные файлы и ответы
анкеты обрабатываются в памяти и на диск не пишутся. Всё состояние сервиса —
это код и модели в `riskml/artifacts/`, которые лежат в репозитории.

Единственное, что стоит беречь, — том с сертификатами Caddy, но и он
восстанавливается сам: при потере Caddy просто выпустит сертификат заново.

---

## Что нужно сделать руками

1. **DNS.** Уже сделано: `shazram.ru` и `www.shazram.ru` → `2.56.120.183`.
   При смене сервера обе записи надо обновить.
2. **Пароль root сменён** — старый, который был в переписке, больше не действует.
   Новый лежит локально в `~/.ssh/shazram_rootpass.txt`; перенесите его в
   менеджер паролей и удалите файл.
3. **SSH-ключ** — `~/.ssh/shazram_ed25519`. Вход по паролю намеренно **оставлен
   включённым**: отключать его, не имея у вас на руках проверенного второго
   способа входа, рискованно. Когда убедитесь, что ключ работает с вашей машины:
   ```bash
   sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
   systemctl reload ssh
   ```
4. **Секреты в репозиторий не коммитить.** `deploy/.env` в `.gitignore`;
   в репозитории только `.env.example`.

## Ресурсы

Замерено на боевом сервере под нагрузкой одного файла в 649 строк:

| Контейнер | RAM | Лимит |
|---|---|---|
| backend | 209 МБ | 1.2 ГБ |
| frontend | 2.5 МБ | 128 МБ |
| caddy | 14 МБ | 128 МБ |

Диск: 6.1 ГБ занято, **3.2 ГБ свободно**. Обработка файла в 649 строк —
около 4 секунд (на локальной машине 2.5 с; разница — одно ядро против восьми).

**Узкие места, по убыванию риска:**

1. **Диск.** Каждая пересборка добавляет ~1.7 ГБ слоёв. `deploy.sh` теперь
   убирает их сам, но если собирать в обход скрипта — место кончится.
2. **Одно ядро.** Сборка фронтенда занимает несколько минут, и во время неё
   сайт отвечает медленнее. Обновляться лучше не в момент показа.
3. **Память при пиках.** Объяснения считаются батчем: файл на 20 000 строк
   (это лимит приложения) даст заметный всплеск. Для демо-файлов запаса хватает,
   лимит в 1.2 ГБ поставлен именно как страховка.
